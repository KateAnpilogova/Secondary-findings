# Ручной режим: docx интерпретатора → PDF

Запасной путь на случай, если отчет не удается собрать из пайплайна. Интерпретатор присылает docx в старом формате, скрипт `docx_to_report.py` достает из него данные, сохраняет JSON участника и собирает PDF тем же `render.py`, что и основной путь. Шаблоны, стили и проверки одни и те же: PDF из docx ничем не отличается от PDF из системы.

```
docx интерпретатора
   │  docx_to_report.py: разбор таблиц и разделов, нормализация значений
   ▼
JSON участника (рядом с docx)      ← можно открыть и проверить, что распозналось
   │  render.render(): те же проверки, Jinja2 → HTML → WeasyPrint
   ▼
PDF (рядом с docx или в -o)
```

## Файлы

| Файл | Что делает |
|---|---|
| `docx_to_report.py` | Разбор docx → JSON → вызов `render.render()`. CLI, режим `--gui` для Finder |
| `finder_action.sh` | Обертка для «Быстрого действия» macOS: задает Python и пути к библиотекам Homebrew, пишет лог |
| `sups/test_docx/` | Тестовые docx: `example_neg.docx`, `example_pos.docx`, реальный `100003175.secondary_rep.docx` и результаты их разбора |
| `output/finder_action.log` | Лог запусков из Finder (создается сам) |

Зависимость сверх `requirements.txt`: `python-docx` (проверено на 1.2.0).

## Запуск

Из терминала (в папке проекта):

```bash
python docx_to_report.py sups/test_docx/example_pos.docx          # JSON и PDF рядом с docx
python docx_to_report.py отчет.docx -o output/                     # PDF в другую папку
python docx_to_report.py *.docx                                    # пачкой
```

На Mac с Apple Silicon перед этим нужен `export DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib` (или эта строка в `~/.zshrc`), иначе WeasyPrint не найдет Pango.

Из Finder: правый клик по .docx → «Быстрые действия» → «Собрать отчет». Результат (путь к PDF или список ошибок) показывается всплывающим окном.

Код возврата из терминала: `0` — все отчеты собраны, `1` — хотя бы один нет. С `--gui` всегда `0` (см. ниже, почему).

## Что ищется в docx

Разделы и таблицы находятся по содержимому, а не по номеру, поэтому порядок блоков и лишние абзацы не мешают. Документ обходится сверху вниз, абзацы и таблицы в том порядке, в каком они стоят в файле.

| Что | Как находится | Во что превращается |
|---|---|---|
| Таблица участника | таблица, где есть «Участник исследования»; значение берется из последней ячейки строки | `participant`; `sex` (Ж/М/жен/муж → `женский`/`мужской`); `date` как есть |
| Таблица вариантов | таблица, где есть слово «Зиготность»; первая строка — заголовок, дальше по строке на вариант, 6 колонок | `variants[]` |
| — «Ген» | все, кроме букв, цифр, `_` и `-`, удаляется | `gene` |
| — «Заболевание» | шестизначное число = OMIM, остальное = название (слово OMIM и `#` вычищаются) | `disease`, `omim` |
| — «Изменение ДНК» | регулярки: `chr6:26092913 G>A` (допускаются `-`, `g.`, `/`), `NM_…:c.…`, `p.…` (скобки `p.(…)` снимаются) | `position`, `hgvs_c`, `hgvs_p` |
| — «Зиготность (Тип наследования)» | словари `ZYGOSITY_MAP`, `INHERITANCE_MAP`: «гомозиготное состояние» → `гомозигота`, «аутосомно-рецессивный» / «АР» / «AR» → `АР` и т. д. | `zygosity`, `inheritance` |
| — «Частота» | `0,0384`, `3,2×10-5`, `3.2x10^-5`; прочерк, «нет», «н/д» → `null`; округление до 3 значащих цифр | `frequency` |
| — «Прочтения» | `21/40` | `reads_alt`, `reads_total` |
| Строка «Не обнаружено.» или объединенная строка | пропускается | вариантов нет, `variants: []` |
| Раздел «ИНТЕРПРЕТАЦИЯ ВАРИАНТОВ» | заголовок = абзац, где ≥ 6 русских букв и все прописные; берутся абзацы до следующего такого заголовка | `interpretation` — по строке на абзац, курсив → `<i>…</i>` |
| Раздел «СПИСОК ЛИТЕРАТУРЫ» (необязательно) | заголовок со словом «литератур» или «источник»; пункты «12. Автор …» или автонумерация Word | `references` (только дополнительные статьи) |
| Таблица тех. характеристик | строка «Средняя глубина прочтения…» | `mean_depth` (`36` → `36×`) |

Из интерпретации выбрасываются стандартные фразы, которые новый шаблон печатает сам (список `BOILERPLATE`): «значимых изменений… не обнаружено», «оценка клинической значимости…», «результаты данного исследования могут быть правильно интерпретированы…».

### Классификация

В таблице docx классификации нет. Если вариант один, она берется из текста интерпретации: есть «вероятно патоген…» → `вероятно патогенный`, иначе есть «патоген…» → `патогенный`. Если вариантов несколько, остается `null`, и в таблице PDF строка классификации не печатается. Ключ `classification` есть у каждого варианта всегда (иначе упадет шаблон).

### Литература

В docx интерпретатор нумерует ссылки сквозняком по своему списку: `[12]`, `[12, 13]`, `[12–14]`. Скрипт (`map_citations()`) переводит их в формат нового шаблона:

- пункт списка совпадает с одним из 11 постоянных источников в `study.json` (текст сравнивается без номера, `https://`, `www.` и точки в конце; ACMG SF узнается по «acmg sf») → ссылка получает номер этого источника (`[3]`);
- иначе это дополнительная статья → маркер `[@ref12]`, а текст пункта уходит в `references` под ключом `ref12`.

Дальше `render.py` сам нумерует дополнительные статьи с 12 по порядку первого упоминания. Номер в PDF может не совпасть с номером в docx, это нормально.

## Когда PDF не собирается

Сначала проверки разбора — при любой из них PDF не собирается:

- файл не читается (битый, не docx);
- не найдена таблица вариантов (нет «Зиготность»);
- нет «Участник исследования», «Пол» или «Дата исследования»;
- в строке варианта не 6 колонок;
- не распознаны `position`, `hgvs_c`, `zygosity`, `inheritance` или прочтения — в сообщении приводится текст ячейки;
- в интерпретации ссылка `[n]`, а пункта `n` в списке литературы нет.

Только предупреждение: нет средней глубины — в отчете будет «—».

Потом — обычные проверки `render.py` (обязательные поля, допустимые значения, `reads_alt ≤ reads_total`, интерпретация при наличии вариантов).

JSON сохраняется рядом с docx даже при ошибке — по нему видно, что распозналось, а что нет. Его можно поправить руками и собрать PDF напрямую: `python render.py отчет.json -o output/`.

## Быстрое действие в Finder

### Как устроено

Automator → `finder_action.sh` → `docx_to_report.py --gui`. Скрипт-обертка нужен, потому что Finder запускает программы без окружения терминала:

- `PYTHON="/opt/anaconda3/bin/python"` — явно указан Python, в котором стоят weasyprint, jinja2, python-docx;
- `DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib…` задается внутри скрипта. Из `~/.zshrc` она бы не дошла: macOS вырезает `DYLD_*` при запуске системных программ вроде `/bin/bash`;
- пути к файлам читаются из stdin по одному на строку (так в Automator не нужны кавычки); последняя строка без перевода строки тоже читается;
- каждый запуск дописывается в `output/finder_action.log` (дата, какие файлы пришли, весь вывод Python).

Почему с `--gui` код возврата всегда `0`: результат уже показан окном, а любой ненулевой код Automator превращает в пустое окно «ошибка: «»». Если Python упал аварийно, `finder_action.sh` показывает свое окно со ссылкой на лог.

Окна показываются через `osascript`; текст передается аргументом (`on run argv`), а не внутри AppleScript, — иначе ломаются кавычки и кириллица.

### Установка (один раз)

1. Проверить из терминала, что работает: `python docx_to_report.py sups/test_docx/example_pos.docx`.
2. Automator → «Новый документ» → «Быстрое действие».
3. Вверху: «Процесс получает: **файлы или папки** в **Finder**».
4. Добавить действие «Запустить shell-скрипт»: оболочка `/bin/bash`, «Передать ввод: **на stdin**».
5. Текст скрипта: `bash ~/PycharmProjects/secondary_findings/finder_action.sh`
6. Сохранить как «Собрать отчет».

Если папку проекта перенесли или сменился Python, поправить путь в шаге 5 и строку `PYTHON=` в `finder_action.sh`.

### Если не работает

| Что видно | Причина / что делать |
|---|---|
| Окно «Файл не передан» | Действие запущено кнопкой внутри Automator или не получило файлов — запускать из Finder по выделенному docx; проверить «на stdin» |
| Окно «Скрипт завершился с ошибкой» | Аварийное падение Python — смотреть `output/finder_action.log` |
| В логе `cannot load library 'libgobject-2.0-0'` | Не найден Pango — проверить `DYLD_FALLBACK_LIBRARY_PATH` в `finder_action.sh` и `brew install pango` |
| В логе `No module named 'docx'` | В Python из `PYTHON=` не стоит python-docx: `/opt/anaconda3/bin/python -m pip install python-docx` |
| PDF без верстки | Не нашелся CSS — пути в шаблонах должны быть от корня проекта (`styles/…`), см. лог `Failed to load stylesheet` |
| «нужен файл .docx» | Прислали .pages: Pages → Файл → Экспортировать → Word |

## Ограничения

- Читается только .docx; .pages и .doc — нет.
- Разбор привязан к формулировкам в шаблоне интерпретаторов («Участник исследования», «Зиготность», «ИНТЕРПРЕТАЦИЯ ВАРИАНТОВ», «Средняя глубина»). Если шаблон docx поменяется, править словари и условия в `parse_docx()`.
- Классификация для нескольких вариантов не определяется.
- Проверено на реальных отчетах без находок и на тестовых с находками; реального отчета с находками еще не было — первый такой стоит сверить с docx глазами.
